# field

A deterministic particle flow field, written in Rust and compiled to
WebAssembly. It is the animated background of the hero on
[joelberus.github.io](https://joelberus.github.io).

I am a TypeScript developer learning Rust. This crate is small on purpose: it
is the first Rust I ship to real users, and I wanted every line to be something
I can explain.

## What it does

A few hundred particles drift through a vector field. The base field is the
curl of a value-noise potential, which makes it divergence-free: it has no
sources or sinks, so the flow tends not to gather particles in obvious clumps.
The pointer adds a local swirl. Particles live for a few seconds and then
respawn somewhere else.

Rust runs the simulation. JavaScript draws it on a 2D canvas.

## Layout

| File           | Role                                                                 |
| -------------- | -------------------------------------------------------------------- |
| `src/rng.rs`   | PCG32 random number generator, about 30 lines, no `rand` crate       |
| `src/noise.rs` | 3D value noise and its 2D curl                                       |
| `src/sim.rs`   | `Field` and `Particle`: stepping, pointer force, resize, respawn     |
| `src/wasm.rs`  | `wasm-bindgen` wrapper, the only code that knows about the browser   |

`rng`, `noise` and `sim` use no WebAssembly types and are marked
`#![forbid(unsafe_code)]`. That is what makes them testable with a plain
`cargo test` on any machine.

## API

Rust core (`field::Field`):

```rust
Field::new(width: f32, height: f32, count: usize, seed: u32) -> Field
field.step(dt: f32)                         // seconds, clamped to MAX_DT
field.set_pointer(x: f32, y: f32, active: bool)
field.resize(width: f32, height: f32)       // scales particles, no allocation
field.set_count(count: usize)               // the only call that may reallocate
field.particles() -> &[Particle]
field.count() / width() / height() / time()
```

JavaScript (`FlowField`, generated by `wasm-bindgen`):

```ts
const wasm = await init();
const field = new FlowField(width, height, count, seed);

field.step(dt);
field.setPointer(x, y, active);
field.resize(width, height);
field.setCount(count);

// A view into WebAssembly memory. No copy is made.
const particles = new Float32Array(
  wasm.memory.buffer,
  field.particlesPtr(),
  field.particlesLen(),
);
// FlowField.stride() floats per particle:
// [x, y, prev_x, prev_y, vx, vy, life, kind]
```

## Design decisions

**Rust owns the buffer, JavaScript borrows it.** The particles live in one
`Vec<Particle>` that the `Field` owns for its whole life. `Particle` is
`#[repr(C)]` and made only of `f32` fields, so the vector is, byte for byte, a
flat array of floats. Compile-time assertions pin that layout: the size and
alignment of the struct and the offset of every field (`offset_of!`), which are
the indices the JavaScript renderer reads. JavaScript gets the address and
length and reads the data in place.

The Rust borrow checker cannot see across this boundary, so the rule has to be
kept by hand on the JavaScript side: the view is stale after `setCount` (the
`Vec` may have moved) and after the WebAssembly memory grows (the old
`ArrayBuffer` is detached). `src/components/field/mount.ts` in this repository
recreates the view in both cases.

**No allocation per frame.** `step`, `set_pointer` and `resize` mutate
particles in place. Tests check that the buffer address is unchanged after
stepping, resizing and moving the pointer, and that the pointer and length
describe the live buffer again after `set_count`. Each frame is one call into
WebAssembly.

**Determinism.** For a given build, the same seed and the same sequence of
calls give the same state. Nothing reads a clock or a system random source; the
generator is part of the state, and respawns consume it in particle order. The
native tests compare whole states, and the list of which particle respawned on
which step, with exact float equality. The generator itself is checked against
the output of the PCG reference implementation.

The scope of that claim is one build on one platform. No test compares a native
build with the WebAssembly build, so I do not claim they agree bit for bit.

**Divergence-free is a property of the field, not of the particles.** The curl
of a potential has zero divergence, and a test checks it numerically. The
particles only follow that field approximately: the curl is estimated with
finite differences, velocities have inertia and a speed limit, the pointer
adds a push that does have divergence, and particles respawn at random places.
The spread looks even; nothing guarantees it.

**No `unsafe`.** Returning a raw pointer is safe in Rust; dereferencing it is
not, and only JavaScript ever reads through it.

## What I practiced

- Ownership of a buffer that outlives every call, and exposing it without
  giving it away.
- Disjoint borrows: `step` destructures `self` so it can iterate the particles
  mutably while also using the random generator mutably.
- Explicit integer overflow (`wrapping_mul`, `rotate_right`) in the generator
  and the hash.
- Keeping a core free of platform types so it can be tested natively, with a
  thin adapter for the platform.
- Size work: `opt-level = "s"`, LTO, one codegen unit, `panic = "abort"`, and
  `wasm-opt`. One lesson from it: while trying `opt-level = "z"`, a single
  `f32::clamp` pulled float formatting into the binary through its panic
  message and took the module from 20 kB to 45 kB.

## Limits

- Value noise is the simplest coherent noise, not the best looking one.
- The curl uses finite differences (four noise samples per particle) instead of
  analytic derivatives.
- Integration is plain Euler with a clamped time step. Fine for decoration, not
  for physics.
- The module still carries Rust's allocator and panic paths, which is most of
  its size. I have not tried `no_std` or a custom allocator.

## Commands

```sh
cargo test                      # unit tests, native
cargo clippy --all-targets -- -D warnings
cargo fmt --check

# From the repository root: build to src/wasm/field and print the size
pnpm run build:wasm
```

Building needs the `wasm32-unknown-unknown` target and `wasm-pack`:

```sh
rustup target add wasm32-unknown-unknown
cargo install wasm-pack
```

Current size of `field_bg.wasm`: about 20 kB raw, 9 kB gzipped. The exact
numbers are printed by the build and shown on the site.
